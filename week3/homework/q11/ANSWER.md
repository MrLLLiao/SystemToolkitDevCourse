# 练习11: 用编程智能体完成"Markdown 无序列表正则"练习，且不直接编辑文件

## 练习要求
用编程智能体完成与"代码质量"一讲中 Markdown 无序列表正则练习**相同的目标**
（用正则匹配/提取 Markdown 无序列表项），但**不通过直接编辑文件**完成；
并思考：智能体直接编辑文件有什么缺点？如何提示智能体不直接编辑文件？（提示：用第一讲讲过的命令行工具。）

## 本练习的"智能体"
我就是那个编程智能体。为了让过程可复现、可审阅，我把任务拆成一条**只读的命令行流水线**
（全部用第一讲《shell 工具与脚本》里的工具：`grep -P`、`sed -E`、`awk`、`md5sum`），
写进 `solve.sh`，所有结果输出到 `stdout/output.txt`，**从头到尾没有改过 `sample.md` 一个字节**。

## 目标（与代码质量一讲同一目标）
匹配 Markdown 无序列表项（`-`/`*`/`+` 开头、可带前导缩进），同时**不误匹配**：有序列表、水平线 `---`、代码块内的 `-`/`*`。

## 它是通过直接编辑文件完成的吗？——不是。
| 步骤 | 命令（只读） | 结果 |
|---|---|---|
| 朴素正则匹配 | `grep -Pn '^\s*[-*+]\s+'` | 9 处（含代码块内 2 行误报） |
| 精确匹配（排除代码块） | `awk '/^```/{in=!in;next} !in && /^[ \t]*[-*+][ \t]+/'` | 恰好 7 处 |
| 负例验证 | 无序正则对有序列表 0、对 `---` 0 | 0 / 0 |
| 提取列表项文本 | `sed -n -E 's/^([ \t]*)[-*+][ \t]+/\1/p'` | 9 行文本（含 2 误报，已注明） |
| 证明未改源文件 | `md5sum` 前后对比 | 一致（7c4caa…） |

关键收获：**正则只能看到"行"，看不到"代码块"这种上下文**；要精确，就得用 `awk` 维护一个
三反引号围栏的布尔状态机（这也是"正则做不了、状态机做得到"的经典例子）。

## 智能体直接编辑文件有什么缺点和局限？
1. **不可审阅/不可复现**：改了就是改了，没有留下"这一步为什么这么改"的过程；换台机器重跑不出同样结果。
2. **破坏性大、难回滚**：一次误替换可能改坏多处；除非有 git，否则很难精确还原。
3. **容易被"上下文"骗**：智能体肉眼定位"第 N 行"容易看错，或用直觉正则误伤（本例代码块就是陷阱）。
4. **不组合、不沉淀**：直接编辑只解决一次；命令流水线可以沉淀成 `solve.sh`，反复使用、进 CI。
5. **放大"幻觉"风险**：直接改写文件时，智能体可能"顺手"改动无关内容或插入新错误，事后难以发现。

## 怎么提示智能体不直接编辑文件？
在任务描述里**显式立规矩**，例如：
- "用第一讲学到的命令行工具（grep/sed/awk/…）以只读方式处理，源文件一个字节都不要改；结果输出到独立文件或 stdout。"
- "完成后用 `md5sum`（或 `git diff`）证明源文件未变。"
- "把每条命令写进可复现的 `solve.sh`，而不是对文件做一次性手工修改。"
- 若确实要改，改为"先输出 diff / 新版本内容，我确认后再落盘"，把"编辑"变成"生成 + 审阅"两步。

这样就把智能体从"手改文件的编辑工"变成"生成可审阅产物的流水线"，既安全又可复现。

## 验证
- `output.txt` 记录了全部命令与结果；`bash solve.sh` 可完整复现。
- 精确匹配 7 处、负例全为 0、`md5sum` 前后一致 → 目标达成且源文件零改动。
