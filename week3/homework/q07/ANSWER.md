# 练习7: 同一编程任务用四种模式各做一次并比较

## 练习要求
把同一编程任务分别用「手动编码、AI 自动补全、内联聊天、智能体」各做一次，比较体验差异。
选择：我当前正在开发的 q07/wordcount 项目（一个 wc 风格命令行工具）中的一个小功能——新增 `--top N`（打印输入文件中出现次数最多的前 N 个词）。

> 诚实说明：本次四种模式都由"我"（同一个模型/智能体）在本环境执行，并完整保留了各模式的输入与产物，
> 以如实对比"同一个人在不同模式下写同一个功能"时的流程、心智负担与验证方式差异。

## 目标功能（四种模式行为目标完全一致）
`python3 wordcount_top.py --top 4 testdata/sample.txt` 输出：
```
       4       18      104
--top 前 N 个高频词 --
    3  hello
    2  the
    1  world
    1  quick
```

## 四种模式的执行与产物
| 模式 | 我做了什么 | 产物 | 主要差异点 |
|---|---|---|---|
| 1 手动编码 | 自己逐行想清 argparse/词法切分/Counter，一次敲完，无任何辅助 | `manual/wordcount_top.py` | 心智负担全在自己；写前已想清方案；几乎不回看 |
| 2 AI 自动补全 | 只敲 import、签名、docstring、参数声明与调用框架，函数体交给补全 | `autocomplete/skeleton.py` + `completed.py` | 写"意图"而非"实现"；补全质量依赖骨架质量；补全内容可能"想当然" |
| 3 内联聊天 | 把问题+约束发给聊天，只把 AI 给的代码片段插到基线 | `inline_chat/prompt.txt` + `ai_reply.txt` + `wordcount_top.py` | 需要把"上下文"在提示词里讲清楚；AI 给片段、人负责"放对位置"；适合局部修改 |
| 4 智能体 | 给一句话任务，智能体自己读代码→计划→实现→真实运行验证 | `agent/task_prompt.txt` + `agent_log.md` + `wordcount_top.py` | 开销在探索与计划；收益是主动验证与结构组织（collect_words 独立成可测函数） |

## 体验差异对比（真实观察）
1. **上下文依赖**：手动/补全几乎不需要"讲背景"；内联聊天要把当前代码结构写进提示词；智能体自己读代码，无需人转述。
2. **心智负担分布**：手动——全程承担；补全——承担"设计意图"、补全承担"填肉"；聊天——承担"提问+落位"；智能体——只承担"定义任务"，其余全外包。
3. **错误与验证**：
   - 手动：写完即跑，发现 `-l/-w/-c` 其实没过滤列（基线遗留 bug），顺手修了；
   - 补全：补出来的函数体与 docstring 声明一致，但若骨架模糊，补全会自行脑补接口；
   - 聊天：AI 建议把 `from collections import Counter` 放在函数内——正确但不够干净（智能体模式会更倾向模块级 import）；
   - 智能体：明确要求"先读代码→计划→验证"，最终把 collect_words 独立成纯函数（可单测），并且主动对照基线确认非 --top 输出无回归。
4. **可复现性/审计**：聊天与智能体留下"提示词+回复/日志"，最可审计；手动与补全留下的只有最终代码。
5. **适用场景**：
   - 手动：想完全掌控、或练基本功；
   - 补全：写"模板化"代码（样板、重复结构）效率最高；
   - 内联聊天：问"某个片段怎么写"、"帮我解释/改这几行"最顺手；
   - 智能体：跨文件、需要探索+验证的任务（加新功能、改接口、重构）最值得。

## 执行中发现的一个真实 bug（顺带修复）
基线 `-l/-w/-c` 只解析了标志却没用它们过滤输出列（三种模式都从基线继承）。修正为按 flags 过滤列后，
四种产物 `-w → 18`、`-l → 4`、`-c → 104` 完全一致（见 output.txt 第 3 节）。

## 验证
- `output.txt`：基线冒烟 + 四种模式 `--top 4` 输出逐字节一致 + `-l/-w/-c` 生效验证 + 产物清单。
- 重跑 `bash solve.sh` 可复现。
